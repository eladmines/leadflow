# F12 — WhatsApp (POC)

Status: **POC built** (branch `whatsapp-poc`). Decision: D-091 (_Proposed_). Full F12 (connection screen,
per-business numbers, inbox page, templates) is still planned.

## Scope of the POC

- One WhatsApp number, connected to one business through environment variables (no UI, no tokens in the DB).
- Meta's webhook → `POST /api/v1/integrations/whatsapp/webhook`, verified with `X-Hub-Signature-256`
  (HMAC of the raw body with the app secret). `GET` answers Meta's verification handshake.
- Incoming message → contact matched by phone (or created with the WhatsApp profile name) → joins the
  contact's latest open lead, or creates a lead with source `whatsapp` in the first stage.
  Meta retries are ignored by message id.
- Lead cards in the list preview the latest WhatsApp message (who wrote it, when).
- The lead page shows the conversation; the team replies while the 24-hour window is open
  (`leads.update`; employees only on leads assigned to them). Delivery receipts update the status
  (never backwards). Media arrives as a label ("[תמונה] caption"); files are not downloaded.
- Adapters: `local` (records sends, used for development and tests) and `cloud` (Graph API).

Not in the POC: notification email for WhatsApp leads, templates (messages outside the window),
media download, several numbers/businesses, a connection screen.

## Acceptance criteria

1. A signed text event creates a WhatsApp lead with the customer's name, phone and first message. ✅
2. Unsigned or wrongly signed events are rejected (401) and store nothing. ✅
3. The same message delivered twice creates one message and one lead. ✅
4. A second message from a customer with an open lead stays on that lead; after the lead is won/lost a new lead is created. ✅
5. A reply inside 24 hours is sent to the customer's number and appears in the thread; outside it the API refuses with a Hebrew explanation (409). ✅
6. Provider errors show a generic Hebrew message; Meta's text and the phone number are never returned or logged. ✅
7. Tenant isolation: outsiders get 404 (route walker), employees see only assigned leads. ✅

## Try it locally (no Meta account)

In `apps/api/.env`: `WHATSAPP_PROVIDER=local`, `WHATSAPP_BUSINESS_ID=<business id>`, any
`WHATSAPP_APP_SECRET` (≥ 16 chars) and `WHATSAPP_VERIFY_TOKEN`. Restart `pnpm dev`, then:

```bash
pnpm --filter @leadflow/api wa:simulate --from 0541234567 --name "נועה" --text "היי, אפשר לקבוע תור?"
```

The lead appears in the CRM; replies are recorded (not delivered) in local mode.

## Try it with Meta's free test number

1. developers.facebook.com → create a Business app → add WhatsApp. Note the test number's
   **Phone number ID**, a token, and **App settings → Basic → App secret**. Add your phone as a recipient.
2. `.env`: `WHATSAPP_PROVIDER=cloud`, `WHATSAPP_PHONE_NUMBER_ID`, `WHATSAPP_ACCESS_TOKEN`,
   `WHATSAPP_APP_SECRET`, `WHATSAPP_VERIFY_TOKEN`, `WHATSAPP_BUSINESS_ID`. Restart.
3. Expose the API: `cloudflared tunnel --url http://localhost:4000` (free) and set Meta's webhook to
   `https://<tunnel>/api/v1/integrations/whatsapp/webhook` with the same verify token; subscribe to `messages`.
4. Link the app to the WhatsApp Business Account so messages reach your webhook. Meta's setup screen may
   not do this (only its own "WA DevX Webhook Events" app is listed):
   `curl -X POST "https://graph.facebook.com/v25.0/<WABA id>/subscribed_apps" -H "Authorization: Bearer <token>"`
   (the WABA id is the "Messaging account ID" on Step 1. Try it out).
5. Send a WhatsApp from your phone to the test number → lead in the CRM → reply from the lead page.

The quick token expires after 24 hours; use a system-user token for longer demos.

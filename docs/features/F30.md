# F30 — Leads and ad tracking for a website built elsewhere

Status: **Built** (first version, 2026-11-23). Decision: D-189 (Accepted).

F26 names the ad behind every lead, but only on sites built in SimpleCatch. A business with a Wix or
WordPress site got nothing. F30 gives it **one script tag**: its forms create leads here, with the ad
that brought each one. No Google or Meta approval is needed.

## What the owner does

Site → (existing website) → "Receive inquiries from your website": paste the `<script>` line before
`</body>`, and mark the contact form with `data-simplecatch`. Fields are found by `name`: `name`,
`phone`, `email`, `message`, `consent` (a checkbox; `data-consent-implied` on the form when its own
text already asks for consent). Each ad link gets the same tags as in F26 ("Connect your ads").

## What the script does (`apps/api/src/modules/embed/script.ts`, plain ES5)

- On landing: reads `utm_*` and click ids from the URL and `document.referrer`; an ad click or tagged
  link replaces what is stored, otherwise the first visit stays (the F26 rule). Kept in
  `localStorage` (`sc_src`) for 30 days. Nothing else on the URL is kept.
- On submit of a `form[data-simplecatch]`: posts the fields with the stored source, shows
  `data-success` text (or a default), and fires `simplecatch:sent` / `simplecatch:error` events.
- `window.SimpleCatch.send(fields, callback)` for form builders that can't carry attributes.

## Forms we did not write: smart field detection (2026-11-23)

A customer's own form (`<input name="n">`, `name="p" type="tel"`, a date, a `textarea name="e"`, a hidden
`_honey` trap, its own way of sending) works without renaming anything. The script finds the fields by
the names we ask for first, then by **type** (`email`, `tel`, `textarea`), and by what a field says about
itself (name, id, placeholder, aria-label, `autocomplete`, its `<label>`), in Hebrew or English:

- name: a field with "name"/"שם" (first and last name are joined, `autocomplete="name"`);
- phone: `type="tel"` or "phone/mobile/טלפון/נייד"; email: `type="email"` or "email/מייל";
- message: the first `textarea`;
- **other filled fields** (an event date, a service, a budget) go into the message as `label: value`
  (a label's "(optional)" is dropped), so nothing the visitor wrote is lost;
- a hidden field (aria-hidden or tabindex -1) named like a trap (`honey`, `hp`, `website`…) is sent as
  the honeypot, so a bot's submission is dropped by the server;
- consent: a tick box named/labelled like consent, or the form's only tick box. **A form with no tick
  box at all counts as consenting: sending a contact form is asking to be contacted** (D-196); a tick
  box that is there and not ticked is not consent. `data-consent-implied` still forces it on.
- a form picked by `data-forms` needs a phone field (found by the same rules, by being there, not by
  having a value); a newsletter box with only an email is left alone.

Labels and field names are only read in the browser to tell fields apart. The only label ever sent is an
extra field's, next to its value.

`data-copy`: for a form that sends itself some other way (a mailer, a fetch), the script only sends a
**copy** (the submit event is not stopped, nothing is replaced, no alert), listening in the capture
phase so it reads the values before the form's own handler can clear them.

Site → existing website has a card for this, "Leads from your form" (which form: `data-simplecatch` or
`data-forms="#id"`, `data-copy`, what is recognised, the two rules above, how to check, and the Shopify
line).

## Shopify (and other builders that can't carry attributes)

Shopify's contact form can't take `data-simplecatch` and posts its fields as `contact[name]`,
`contact[email]`, `contact[phone]`, `contact[body]`. The script understands those names, and the tag
takes options: `data-forms="form[action*='/contact']"` binds forms by CSS selector (only those with a
phone field, so a newsletter box is left alone), `data-consent-implied` and `data-passthrough` (after
ours, the form is submitted normally, so Shopify still gets the message). The Site card shows this
tag under "Shopify store" with the steps (Online Store → Themes → Edit code → `layout/theme.liquid`).
Limits: Shopify's checkout blocks external scripts (visits count on the storefront only); an inquiry
becomes a lead only if the form has a phone (required in the form) and consent text; orders and
customers are not imported. `apps/web/src/features/site/embed-script.test.ts` runs the script in jsdom.

## The endpoint

- `GET /api/v1/embed/sc.js` — the script (cacheable, CORS `*`). It was `lead.js` while it only took leads; renamed neutrally on 2026-11-23, before anyone had pasted it, so no old name is kept.
- `POST /api/v1/embed/lead` — JSON in a `text/plain` body (a CORS "simple request": no preflight),
  `{ key, id, name, phone, email?, message?, consent, website?, params?, referrer?, landing?, page? }`.
  Answers `{ ok }` or `{ ok: false, errors }` (in the business's language), always with CORS `*`.
- The server validates with the same lead schema as a site form, names the source with
  `classifyAttribution` (F26), and creates the lead through `LeadService.createFromWebsite` with no
  `siteId` (deduplicated per business and `id`). Owners and managers get the in-app notification and
  the new-lead email, exactly like a site lead.
- `GET /api/v1/businesses/:id/embed` — the key and the script tag (owner only).

## Safety

- The key is `business id + HMAC(FORM_TOKEN_SECRET)`: stateless, unguessable for other businesses, and
  public by design (it sits in the site's HTML); it can only add leads. A wrong key is a plain 400.
- Honeypot field, per-IP rate limit (`LEAD_FORM_RATE_LIMIT_*`), 16 KB body limit, one id per form view.
- No cookies are read or set, so the CSRF header isn't needed on this one path (it is exempt in
  `plugins/csrf.ts`). Click id **values** are never stored or logged, only their kind; no personal data
  in the stored source.
- Consent: a tick box that is there must be ticked; a form with no tick box counts as consenting (see
  above). `data-consent-implied` forces it on.

## Not in this version

Key rotation (changing `FORM_TOKEN_SECRET` rotates every key), per-site allowed origins, spam scoring,
the Google Ads API (cost per lead, offline conversions: needs Google's approval), file uploads.

## Acceptance criteria

1. The owner sees the script tag in Site (existing website); others don't.
2. A form on another origin creates one lead (a double click too) with source, campaign, keyword and
   landing path; the click id value is not stored.
3. Organic Google, another site and direct visits are named like F26; direct keeps none.
4. A wrong key, a missing consent, a bot (honeypot) and a garbage body create no lead; errors are in the
   business's language.
5. Existing site forms behave as before (shared `createFromWebsite`, `notifyTeamByEmail`).

# F34 — Custom lead fields

Status: **In progress (architect done)** (approved 2026-11-27; contract frozen 2026-11-27).
Decisions: D-203 (Accepted), D-205 (Accepted: required only in the full dialog and lead-card edits;
import mapping later), D-204 (Proposed, contract details; see "Contract" below).

Every lead has the same fixed fields (name, phone, message, expected value, tags). Businesses need
their own: an events business wants the event date, guests and budget; a garage wants the car model;
a clinic the type of treatment. Today that goes into the message or into tags, where it can't be
filtered, sorted or reported. F34 lets each business define its own lead fields.

## What the owner does

Settings → "Lead fields": add a field with a label, a type and (for a choice) its options; reorder
by drag or arrows; archive a field. Owners and managers manage fields; anyone who may edit a lead
fills them in.

## Field types (first version)

| Type      | Stored as              | Notes                           |
| --------- | ---------------------- | ------------------------------- |
| `text`    | string, max 500        | one line                        |
| `number`  | number                 | optional min/max                |
| `date`    | `YYYY-MM-DD` string    | no time                         |
| `select`  | option **id** (string) | 2–30 options, each label max 60 |
| `boolean` | `true` / `false`       | a checkbox                      |

Out of this version: multi-select, file, phone/email (they are already fixed fields), formulas,
conditional fields.

## Rules

- **Up to 20 active fields per business.** Label 1–40 characters, unique among the business's
  active fields (case-insensitive).
- **Values are keyed by the field's id, never its label.** Renaming a field, or an option, changes
  only the label; existing values keep working.
- **The type can't be changed** after creation. Create a new field instead.
- **Archive, don't delete.** An archived field disappears from forms, filters and New lead; leads that
  have a value still show it, read-only, under "Archived fields". It can be restored. Removing an
  option works the same way: old values still show their label.
- **Required** applies when a person creates or edits a lead in the app. Leads that arrive from the
  website, WhatsApp, Messenger, email, import or the embed script are never rejected for a missing
  custom field.
- **Only the full forms enforce required (D-205).** The full New lead dialog and edits on the lead
  card enforce required fields. Quick "add customer" paths in the app (e.g. the quote screen's
  add-customer dialog) skip them, saying so explicitly in the request
  (`skipRequiredCustomFields: true`); every value they do send is still validated.
- Labels are the business's own text: shown as written, **not** passed through `tr()`, with `dir="auto"`.

## Data model

- New table `lead_field_definitions`: `id`, `business_id`, `label`, `type`, `options` (JSONB:
  `[{ id, label, archived_at? }]`), `required`, `position`, `created_at`, `updated_at`,
  `archived_at`. Index on `(business_id, archived_at, position)`.
- `leads.custom_fields JSONB NOT NULL DEFAULT '{}'`: `{ "<definition id>": <value> }`. A GIN index
  (`jsonb_path_ops`) for filtering. A key whose value is empty is removed, not stored as `null`.
- The server validates a lead's `custom_fields` against **that business's** definitions (unknown
  key, wrong type, unknown option, over-length → `VALIDATION_ERROR` with a Hebrew message per field,
  in `fields`). The shared Zod schemas describe a definition and a value's shape; the per-business
  check is built from the definitions on both sides.

## API (tenant routes)

- `GET    /businesses/:businessId/lead-fields` — active and archived definitions (`leads.view`).
- `POST   /businesses/:businessId/lead-fields` — create (`leadFields.manage`).
- `PATCH  /businesses/:businessId/lead-fields/:fieldId` — label, options, required, archive/restore
  (`leadFields.manage`). `type` is not accepted.
- `PUT    /businesses/:businessId/lead-fields/order` — the new order of ids (`leadFields.manage`).
- Leads: `custom_fields` on lead create, update and read; the list filter takes
  `cf[<fieldId>]=<value>` (text: contains; select/boolean: equals; number/date: `from`/`to`).

New permission `leadFields.manage`: OWNER, MANAGER. A field from another business → 404.

## Where fields show

- Lead card: a "Details" block with each active field (editable inline) and archived values.
- New lead dialog: the active fields, required ones marked.
- Leads list: a filter per field in the Filter panel; optionally one or two fields as columns
  (chosen per user, stored locally).
- History: changing a custom field writes a `lead.updated` activity with the field id and the old and
  new value.
- Export (`leads.export`): one column per active field, with its label as the header.

## Privacy

Custom values can hold personal data (a plate number, a medical treatment). They are covered by F14
(export, deletion, retention) like the lead itself, deleted with the lead, never logged (add
`custom_fields` to the logger redaction), and never sent to an analytics or tracing attribute.

## Later (not in this version)

- **Website form (F07) and embed script (F30):** the owner adds a custom field to the site's form, or
  maps an embed form's extra field to one, instead of folding it into the message. Biggest win; it
  touches the site builder, so it comes second.
- **AI and the booking bot (F16):** fill fields from the conversation ("how many guests?").
- **Reports (F20):** leads and won value by a select field.
- **Import mapping (D-205):** mapping a spreadsheet column (`customers.import`, D-179) to a custom
  field comes later, with the import screen's design. Imported leads get no custom values in this
  version.
- Custom fields on contacts; multi-select; per-field permissions.

## Acceptance criteria

1. An owner and a manager can add, rename, reorder, archive and restore fields; an employee can't
   (server returns 403/404 as the matrix says; the Settings screen shows the no-permission state).
2. A 21st active field, a duplicate label, an empty label and a type change are refused with Hebrew
   messages.
3. Creating and editing a lead in the app saves values of every type; a wrong type, an unknown option
   and an unknown field id are refused per field. A required field blocks saving in the app only.
4. Renaming a field or an option keeps existing values; archiving hides the field from New lead and
   filters, and its values still show on old leads.
5. Website, WhatsApp, Messenger, email, embed and import leads are created as before without custom
   values.
6. The leads list filters by each type; employees still see only their own leads.
7. A business never sees, reads, filters on or writes another business's fields (cross-tenant walker
   covers the new routes; a foreign field id in `custom_fields` is refused).
8. History shows field changes; export includes the active fields.
9. RTL and LTR, mobile (375px), keyboard and screen-reader labels on the Settings screen and the lead
   card; loading, empty, error and no-permission states.

| Method | Path                                            | Permission                 | Request                              | Response                                                                        | Errors                                                                                                                                                                                                                                                                                                                                                            |
| ------ | ----------------------------------------------- | -------------------------- | ------------------------------------ | ------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |

Behaviour:

- Errors use the shared shape. Per-value errors are keyed `customFields.<fieldId>` (the API joins the
  path with `.`, like Pydantic errors); a non-object or > 100 keys is `customFields`.
- **Values on create (app):** `validateCustomFields(defs, body.customFields, createLeadCustomFieldsOptions(body))`
  with all the business's definitions (active + archived). Empty values dropped.
  `createLeadCustomFieldsOptions` gives `{ mode: 'create', fromApp: !body.skipRequiredCustomFields }`:
  - `skipRequiredCustomFields` absent or `false` (the full New lead dialog, the default): every
    active required field is needed.
  - `skipRequiredCustomFields: true` (quick "add customer" paths, D-205): required fields aren't
    demanded; unknown/foreign ids, wrong types, unknown or archived options and over-length values
    are still refused per field.
  - The flag is a boolean (anything else → 400 `VALIDATION_ERROR`); it isn't stored and isn't on
    PATCH (lead-card edits always enforce required).
- **External sources** (website form, WhatsApp, Messenger, email, embed, import) don't send custom
  values in this version; they insert `{}` (the column default) and are never rejected for a
  required field (`fromApp: false` if anything is ever passed).
- **Characters that can't be stored:** NUL (`\u0000`) or a lone UTF-16 surrogate in a field label,
  an option label, a text value or a text filter value is refused with
  `leadFieldMessages.invalidCharacters` (`hasInvalidCharacters(s)`): 400 `VALIDATION_ERROR` with
  `fields.label`, `fields["options.<i>.label"]`, `fields["customFields.<id>"]` or
  `fields["cf[<id>]"]`. In Python the check is `\x00|[\ud800-\udfff]` on the decoded string.
- **Options on create:** a non-select field may omit `options` or send `[]` (stored `[]`); a
  non-empty list on a non-select field is `optionsNotAllowed`; a select field needs 2–30
  (`optionsCount`).
- **Values on update:** `mode: 'update', fromApp: true, existing: lead.custom_fields`; the result is
  a patch (`null` = remove) merged with `applyCustomFieldsPatch`; keys not sent stay. Only an actual
  change writes history and bumps `updated_at`.
- **Archiving a field** keeps values on leads; GET still returns it (with `archivedAt`); its values
  stay in `customFields`. Restoring puts it last and re-checks the 20 limit and label uniqueness.
- **Options** are stored as `[{ "id", "label", "archived_at"? }]` (DB JSON) and sent as
  `{ id, label, archivedAt }`; option ids are server-generated (uuid4 string) and never reused.
- **Employees:** read definitions (`leads.view`) and fill values on leads they may update; they see
  custom values only on leads they can see (the existing visibility rule).

### List filter query

Next to the existing `leadListQuerySchema` params (bracket keys aren't in that schema; the API reads
them from the raw query string):

| Field type | Params                                          | Meaning                                                                                   |
| ---------- | ----------------------------------------------- | ----------------------------------------------------------------------------------------- |
| text       | `cf[<id>]=<text>`                               | value contains text, case-insensitive (`custom_fields->>id ILIKE %text%`, escape `%`/`_`) |
| select     | `cf[<id>]=<optionId>`                           | equals (`custom_fields @> {"id": "opt"}`, uses the GIN index); archived options allowed   |
| boolean    | `cf[<id>]=true` / `false`                       | ticked / not ticked (`@> {"id": true}` / `NOT ...`)                                       |
| number     | `cf[<id>][from]=<n>`, `cf[<id>][to]=<n>`        | inclusive range; compare only where `jsonb_typeof = 'number'`                             |
| date       | `cf[<id>][from]=YYYY-MM-DD`, `cf[<id>][to]=...` | inclusive range (ISO strings compare as text)                                             |

Key regex `LEAD_FIELD_FILTER_PARAM_RE`; at most 20 fields; values ≤ 100 characters; empty values
ignored. Unknown, foreign or archived field id, a `value` on number/date, `from`/`to` on other types,
a non-number/non-date bound, or a select id not among the field's options → 400 `VALIDATION_ERROR`
with `fields["cf[<id>]"] = leadFieldMessages.filterInvalid` (D-204); a value with NUL or a lone
surrogate → the same with `invalidCharacters`. `leadFieldFilterParams` and
`parseLeadFieldFilterParams` drop such values, so the web never sends them. Filters combine with AND and with
the employee visibility rule. The same filters apply to `GET /leads/export.csv`.

### History (activity payload)

A PATCH that changes custom values writes (in the same `lead.updated` activity as any fixed-field
change):

```json
{
  "fields": ["tags", "customFields"],
  "customFields": [{ "fieldId": "<uuid>", "from": "opt-1", "to": null }]
}
```

`from`/`to` are stored values (`null` = no value; select = option id). The web resolves labels from
`GET /lead-fields` (archived fields and options included). Schema: `leadUpdatedActivityDataSchema`;
`diffCustomFields(before, after)` produces the list. A lead created with custom values writes no
extra activity (the values are on the lead).

### Export (`leads.export`)

One column per **active** field in `position` order, header = the field's label as written;
select → option label (archived option label too), boolean → `כן` / empty, number as is, date
`YYYY-MM-DD`. Same CSV-injection escaping as the other columns.

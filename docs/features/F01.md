## User story and value

As a business owner, I can create an account and sign in securely, so that only I (and people I
invite later) can reach my business data. Every other feature depends on it.

## Scope

Register, login, logout, current user, soft email verification (D-002), resend verification,
forgot/reset password, session management, rate limits, CSRF guard, auth audit events.

## Exclusions

Phone/SMS verification (D-015), social login, MFA, invites (F09), account deletion (F14),
changing email or password while signed in, a "my sessions" screen, a password-changed
notification email (O-008).

### Validation rules

| Field                                | Rule                                                                                           |
| ------------------------------------ | ---------------------------------------------------------------------------------------------- |
| `email`                              | `.trim().toLowerCase()` first, then required, ≤ 254, valid email. Same schema everywhere.      |
| `password` (register), `newPassword` | Required, 10–128 characters, **not** trimmed.                                                  |
| `password` (login)                   | Required, ≤ 128. No minimum (a policy change never locks anyone out; no policy hint on login). |
| `fullName`                           | Trimmed, 2–100 characters.                                                                     |
| `acceptTerms`                        | `boolean`, must be `true` (a boolean + refine, so forms can default it to `false`).            |
| `token`                              | 43-char base64url (`AUTH_TOKEN_PATTERN`). Malformed → same message as unknown/expired.         |

**Email normalisation:** ZodString's built-in `trim`/`toLowerCase` are string → string steps, not
transforms, so the input and output types are identical (`useForm<RegisterRequest>` just works).
The API uses the parsed body, so the stored and looked-up email is always normalised. The `users.email`
unique index therefore is case-insensitive in practice; no `citext` needed.

### Common rules for every endpoint

- **CSRF** (all `POST/PUT/PATCH/DELETE`, authenticated or not): header `X-Requested-With` must be
  present and non-empty (the web sends `LeadFlow`), and `Origin`, **if present**, must be in
  `WEB_ORIGINS`. Otherwise **403 `FORBIDDEN`**. Checked before body validation and before auth.
- **Auth required** = a valid `lf_session` cookie. Missing/expired/revoked/unknown → **401
  `UNAUTHENTICATED`** (`defaultErrorMessages.UNAUTHENTICATED`).
- **Validation** → 400 `VALIDATION_ERROR` with `fields` (field → Hebrew message from the schema).
- **Rate limited** → 429 `RATE_LIMITED`. Per client IP **per route**, `AUTH_RATE_LIMIT_MAX`
  requests per `AUTH_RATE_LIMIT_WINDOW` ms. Every request counts (success or failure).
- Error bodies use the shared shape `{ error: { code, message, fields?, requestId } }`.
- Successful bodies are serialized through the response schema (unknown fields stripped). Dates
  must be converted to ISO strings (`toISOString()`) before returning.

### Endpoints

| #   | Method | Path (`apiPaths.auth.*`)                                       | Auth | Body schema                  | Success                                                                               | Errors                                                                                                           | Rate-limited |
| --- | ------ | -------------------------------------------------------------- | ---- | ---------------------------- | ------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------- | ------------ |

| 2   | POST   | `/api/v1/auth/login` (`login`)                                 | No   | `loginRequestSchema`         | **200** `MeResponse`; sets cookie                                                     | 400 · **401 UNAUTHENTICATED `authMessages.invalidCredentials`** (no `fields`) · 403 · 429                        | Yes          |
| 3   | POST   | `/api/v1/auth/logout` (`logout`)                               | No\* | none                         | **204**; revokes the current session (if any); clears cookie                          | 403                                                                                                              | No           |
| 4   | GET    | `/api/v1/auth/me` (`me`)                                       | Yes  | —                            | **200** `MeResponse`                                                                  | 401 (also clears an invalid cookie)                                                                              | No           |
| 5   | POST   | `/api/v1/auth/verify-email` (`verifyEmail`)                    | No   | `verifyEmailRequestSchema`   | **204**; sets `email_verified_at` (if not set); consumes the token                    | 400 VALIDATION_ERROR `fields.token = authMessages.tokenInvalid` (unknown, used, expired, wrong type) · 403 · 429 | Yes          |
| 6   | POST   | `/api/v1/auth/resend-verification` (`resendVerification`)      | Yes  | none                         | **204**; sends a new verify email. | 7   | POST   | `/api/v1/auth/password-reset/request` (`passwordResetRequest`) | No   | `passwordResetRequestSchema` | **204 always** (unknown email or blocked user: no email, same timing as possible)     | 400 (malformed email only) · 403 · 429                                                                           | Yes          |
| 8   | POST   | `/api/v1/auth/password-reset/confirm` (`passwordResetConfirm`) | No   | `passwordResetConfirmSchema` | **204**; new hash; consumes token; **revokes all the user's sessions**; clears cookie | 400 `fields.token = authMessages.tokenInvalid` · 400 `fields.newPassword` · 403 · 429                            | Yes          |

\* Logout is idempotent: with no or an invalid cookie it still returns 204 and clears the cookie.

Endpoint details:

- **Register**: creates `User` (status ACTIVE, `email_verified_at` null), hashes with argon2id,
  creates a session, issues an `EMAIL_VERIFY` token (24 h) and sends the verify email. If the
  email send fails, registration still succeeds (log the error without the token; the user can
  resend). Duplicate email → 409 (also on a race: map Prisma `P2002` to 409). Note: 409 reveals
  that an email is registered; this is accepted by the docs' test list.
- **Login**: unknown email, wrong password and `BLOCKED` user all return the identical 401. For an
  unknown email still run an argon2 verify against a fixed dummy hash, so timing doesn't reveal
  account existence. If the request already carries a valid session cookie, revoke that session
  before issuing the new one (no session fixation; same for register).
- **Verify email**: no session needed (link may open in another browser). Token must be type
  `EMAIL_VERIFY`, unused, unexpired, user ACTIVE. On success mark **all** of the user's unused
  `EMAIL_VERIFY` tokens used. A second click on the same link → 400 (the web handles this, see
  frontend task 6).
- **Resend verification**: issues a new token; previous unused verify tokens stay valid until they
  expire (any of them verifies).
- **Reset request**: if the user exists and is ACTIVE: mark previous unused `PASSWORD_RESET`
  tokens used (only the newest link works), issue a new one (30 min), send the email. A failed
  send is logged (without the token) and the response is still 204. The status and body never
  differ between existing and unknown emails.
- **Reset confirm**: token must be `PASSWORD_RESET`, unused, unexpired; user ACTIVE. In one
  transaction: update `password_hash`, mark the token (and other unused reset tokens) used, set
  `revoked_at` on all of the user's sessions. Also sets `email_verified_at` if null (the user just
  proved inbox ownership; D-021). The user is **not** signed in; the web sends them to `/login`.

### Response body

```json
{
  "user": {
    "id": "6f1c2b8e-2d3a-4c5b-9e7f-0a1b2c3d4e5f",
    "email": "dana@example.com",
    "fullName": "דנה כהן",
    "emailVerified": false,
    "createdAt": "2026-10-27T10:00:00.000Z"
  }
}
```

`emailVerified = email_verified_at !== null`. Never returned: `passwordHash`, `status`, session or
token data.

## Session cookie

| Attribute | Value                                                                                    |
| --------- | ---------------------------------------------------------------------------------------- |
| Name      | `lf_session` (`SESSION_COOKIE_NAME`)                                                     |
| Value     | 32 random bytes, base64url (43 chars). Unsigned (opaque; looked up by SHA-256 hex hash). |
| HttpOnly  | Yes                                                                                      |
| SameSite  | `Lax`                                                                                    |
| Secure    | `COOKIE_SECURE` (true in production)                                                     |
| Path      | `/`                                                                                      |
| Domain    | Not set (host-only)                                                                      |
| Max-Age   | 90 days (`SESSION_ABSOLUTE_TTL_MS / 1000`) at issue; not re-sent on sliding              |

- **Set** on register and login. **Cleared** (same Name/Path, `Max-Age=0`) on logout, on reset
  confirm, and whenever a presented cookie is invalid (unknown hash, revoked, expired, user
  BLOCKED).
- **Validity**: `revoked_at IS NULL AND now < expires_at AND now < absolute_expires_at AND user.status = ACTIVE`.
- **Sliding**: on an authenticated request, if `now - last_seen_at > 1 h` (write throttle), set
  `last_seen_at = now`, `expires_at = min(now + 30 d, absolute_expires_at)`. The idle window is
  enforced server-side; the cookie's own Max-Age is only an upper bound.
- Session rows store `ip` (`req.ip`, trustProxy is on) and `user_agent` (truncated to 512).

## Database changes

Models are in `apps/api/prisma/schema.prisma` (backend generates the migration):

- `users`: id (uuid), email (unique, varchar 254, normalised), password_hash, full_name (varchar 100),
  email_verified_at, status (`UserStatus` ACTIVE/BLOCKED), created_at, updated_at.
- `sessions`: id, user_id → users (cascade), token_hash (char 64, unique), expires_at,
  absolute_expires_at, last_seen_at, ip, user_agent, revoked_at, created_at; index (user_id).
- `auth_tokens`: id, user_id → users (cascade), type (`AuthTokenType` EMAIL_VERIFY/PASSWORD_RESET),
  token_hash (char 64, unique), expires_at, used_at, created_at; index (user_id, type).
- `audit_logs`: id, business_id (nullable uuid, no FK until F02), actor_user_id → users
  (nullable, `SET NULL`), action, entity_type, entity_id, metadata (jsonb, default `{}`),
  created_at; indexes (business_id, created_at), (actor_user_id, created_at).

All timestamps are `timestamptz(3)`. `users`, `sessions` and `auth_tokens` are platform-level, not
tenant-owned, so they have no `business_id` (tenant isolation unaffected).

## Tests

API (integration):

- Register → 201, cookie attributes (HttpOnly, SameSite=Lax, Path=/, Max-Age, Secure per
  `COOKIE_SECURE`), user has `emailVerified=false`, one email captured with a valid link, audit row.
- Email normalisation: register `Dana@X.com ` then login `dana@x.com` succeeds; register
  `DANA@x.com` again → 409 `fields.email`.
- Duplicate email → 409 with a field error. Weak (9-char) and 129-char passwords → 400.
  `acceptTerms: false` → 400 `fields.acceptTerms`.
- Wrong password, unknown email and BLOCKED user give the same status, code and message.
- Expired (idle and absolute), revoked and tampered sessions → 401 and the cookie is cleared.
  Logout revokes server-side (old cookie → 401). Logout without a cookie → 204.
- Sliding: a request after > 1 h moves `expires_at`, never past `absolute_expires_at`.
- Login while signed in revokes the previous session.
- Verify token: works once (second use 400), expired → 400, a reset token on verify → 400,
  malformed → 400 with the same message. Verify works without a session.
- Resend: 401 anonymous; 204 + email when unverified; 204 and no email when verified.
- Reset request: 204 and no email for an unknown email; 204 + email for a known one; a second
  request invalidates the first link.
- Reset confirm: single-use; expired after 30 min → 400; revokes **all** sessions; old password
  fails, new one works; sets `email_verified_at`.
- Rate limit → 429 `RATE_LIMITED` (configure a low `AUTH_RATE_LIMIT_MAX` in the test).
- CSRF: POST without `X-Requested-With` → 403; with a foreign `Origin` → 403; with an allowed
  Origin or no Origin + header → passes. GET `/me` needs neither.
- Response bodies never contain `passwordHash`, `tokenHash` or `status`.
- Logs contain no password, token or cookie (assert on captured log output).

Web (component): see frontend task 8.

## Acceptance criteria

- [ ] A new user registers in Hebrew UI, is signed in, and the verification email arrives in Mailpit.
- [ ] The verification banner disappears after clicking the email link.
- [ ] Forgot → email → reset → login works end to end; old sessions are invalid.
- [ ] Refreshing the browser keeps the user signed in; logout signs out on the server.
- [ ] No secret, token or password appears in logs or API responses.
- [ ] Email is case- and whitespace-insensitive at register, login and reset.
- [ ] Clicking a verify or reset link a second time, or after it expires, shows a clear Hebrew
      "link invalid" state with a way to get a new link.
- [ ] Forgot-password shows the same confirmation for registered and unregistered emails.
- [ ] A signed-in user opening `/login` or `/register` is sent to `/app`; an anonymous user
      opening `/app` is sent to `/login` and returns to `/app` after signing in.
- [ ] Every auth screen works at 375 px, by keyboard, RTL, with emails shown `dir="ltr"`.

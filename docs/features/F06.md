## User story and value

As an owner, I choose a LeadFlow subdomain and publish with one click; visitors see a fast
HTTPS site, and a failed publish never breaks what's already live.

## Scope

- Subdomain selection: globally unique, validated, reserved words blocked (D-012 locally: `*.lvh.me`).
- Publish: validate the draft → render every page → write an immutable snapshot to storage →
  create `site_versions` → atomically switch `published_version_id` → audit event.
- Version history, rollback to a previous version, unpublish (suspend serving).
- Public serving by Host: published HTML, 404 page, `robots.txt`, `sitemap.xml`, SEO meta,
  cache headers. Local: a public-site server in the API; production: Worker + R2 (deploy task).
- Builder UI: publish button with confirmation, last-published time, error state with a reason.

## Exclusions

Custom domains and SSL issuance (F11); analytics (F20).

## Database changes

`site_versions` (business_id, site_id, version number, storage prefix, created_by, created_at,
status) · `sites.published_version_id`, `sites.subdomain` unique.

## API contracts (draft)

`PUT /businesses/:id/site/subdomain` · `POST /businesses/:id/site/publish` (idempotency key) ·
`GET /businesses/:id/site/versions` · `POST /businesses/:id/site/versions/:vid/rollback` ·
`POST /businesses/:id/site/unpublish` · public: `GET http://{subdomain}.lvh.me:4100/*`.

## Tests

A failed render or storage write leaves the old version live; concurrent publishes give one
winner; republishing site A doesn't touch site B's files; the subdomain conflict message;
public 404; rendered HTML escapes user content; e2e publish → open the public URL.

## Acceptance criteria

- [ ] The site goes live on a subdomain and shows current content (AC-02).
- [ ] Editing the draft after publishing doesn't change the live site until the next publish (AC-03).
- [ ] A failed publish keeps the previous version live and shows the reason (doc 06).
- [ ] Rollback restores an earlier version; other businesses' sites are unaffected.
